# Sol Cabinet v1.5.5-lab.4

状态：LAB（实验态，不是正式发布）

本版本继承 v1.5.5-lab.3 已有实验覆盖，只修复一个高优先级机制问题：

> **v1.5.4／既有 LAB 的 Evolution Engine 存在，但生产收尾入口依赖“主 Agent 自己先意识到发生了真实失败”，且普通观察默认静默，导致自进化可能未触发、未记录或用户无法确认是否执行。**

LAB.4 不重写 Evolution Engine，不扩大自动写权限，不降低 Stable 晋升门禁；只把“发现 → 触发 → 可见状态”做成确定的轻量收尾门。

---

## 1. 实验目标

### 1.1 必须解决的问题

每次 Cabinet 任务完成前都必须经过一次 **Evolution Checkpoint**，不再依赖模型“顺便想起来”。

Checkpoint 必须同时满足：

- 正常任务几乎零额外执行成本；
- 不因自进化而重读文件、重跑验收或扫描维护账本；
- 有真实问题时不能静默消失；
- 记录失败时不能伪装成已记录；
- 用户能从完工小结的一行状态直接确认进化入口是否执行；
- 不改变既有 candidate → Stable 必须用户 FINAL 的权限边界。

### 1.2 模型无关性要求

LAB.4 的 Checkpoint 必须足够浅、足够确定，不能把“换更强模型”当作修复方案。

当前支持的实际执行模型如果能够完成 Cabinet 主任务，也必须能够执行这个固定收尾门。后续真实任务若出现“成品完成但没有进化状态行”，直接判为 **LAB.4 失败信号**，而不是先归因于用户忘记要求。

Luna 与 Sol 的能力差异可以作为后续诊断变量，但不作为跳过 Checkpoint 的理由。

---

## 2. Evolution Checkpoint

### 2.1 运行时点

在真实交付验收完成后、最终完工小结发送前，且每个任务只运行一次。

### 2.2 CLEAN 快路

只使用当前任务已经发生且主 Agent 已知的事实做一次分类。

没有真实系统问题时：

`Checkpoint → CLEAN → 一行状态 → 交付并停止`

禁止为了证明 CLEAN 而：

- 重新读取原稿或成品；
- 再跑 OCR、渲染、公式、哈希或目录检查；
- 读取 observations / proposals；
- 调用 `evolve.py status`；
- 跑回归；
- 写 incident、日志或旁文件。

### 2.3 事故路径

已知发生用户纠正、漏项、假完成、质量失败、误路由、角色未执行、不必要串行、重复读取／检查、规则未生效、运行时兼容、质量退化、任务低估级或交付失控时：

`Checkpoint → 修完当前任务 → 加载 Evolution → 脱敏 capture / record → RECORDED 或 PENDING → 一行状态 → 交付`

- `RECORDED` 只表示安全入队，不表示已修复；
- 写入、证据或门禁失败只能是 `PENDING`；
- 不创建后台任务弥补 PENDING；
- 普通单次事故按既有规则只记录；重复或高影响达到既有门槛后再进入分析／候选；
- 生产 Agent 仍不得直接改 Skill。

### 2.4 用户可见状态

完工小结最后只显示一行：

- `进化：CLEAN`
- `进化：RECORDED｜N项`
- `进化：PENDING｜N项`
- 正式晋升成功时才允许 `进化：EVO-...`

不输出 incident 细节、业务正文、姓名、单位、附件名或业务路径。除用户明确要求，不生成长篇“自我反思报告”。

## 3. 本轮明确不改

LAB.4 不修改：

- v1.5.4 的 Evolution Engine 权限笼；
- `record / regress / resolve / promote / rollback / recover` 的核心脚本语义；
- Stable 必须用户 FINAL 才能晋升；
- 生产任务不得直接修改 Skill；
- 隐私与脱敏要求；
- LAB.3 的 LAB-first、Runtime 身份和 workspace 命名规则；
- T1-T10、Office、Review、Router 的现有质量边界；
- 其他 AI 系统边界。

---

## 4. 回归与真实验收

仓库回归新增 `RC-EVOLUTION-TRIGGER-001`，验证规则链至少具备：

1. Checkpoint 是每次收尾硬门，不是可选提醒；
2. `CLEAN` 不触发维护 I/O、incident、回归或 EVO；
3. 已知真实事故不能以 `CLEAN` 静默结束；
4. 记录成功与失败分别只能是 `RECORDED` / `PENDING`；
5. 四种状态不能互相冒充，尤其普通记录不能冒充 EVO；
6. 状态行不泄露业务敏感信息。

真实生产验证重点看：

- 正常任务是否稳定出现 `进化：CLEAN`，且没有额外机械折返；
- 出现真实执行问题时是否稳定出现 `RECORDED` 或 `PENDING`；
- Luna 实际运行时是否仍会漏掉 Checkpoint；
- Sol 作为对照时是否存在同类遗漏；
- 无论模型，成品质量、验收和墙钟不能因 Checkpoint 明显退化。

若 LAB.4 仍出现“任务已完成但无进化状态行”，或已知事故被错误标成 CLEAN，则本轮结论不能为 KEEP。

结论仍只允许：`KEEP`、`OBSERVE`、`REVERT`。
