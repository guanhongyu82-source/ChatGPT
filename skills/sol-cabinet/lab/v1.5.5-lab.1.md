# Sol Cabinet v1.5.5-lab.1

状态：LAB（实验态，不是正式发布）  
生产基线：v1.5.4  
实验分支：`lab/v1.5.5-lab.1`  
正式发布目标：经真实工作验证、用户定稿后再形成 v1.5.5。

## 1. 实验目标

本轮不重写 v1.5.4 已有的 T1-T2 快车道，而是解决“规则已经存在但执行没有稳定落地”的问题，并重新定义日常自我进化与正式版本优化之间的关系。

核心假设：

1. T1-T2 的质量标准保持不变，通过减少无收益规划、重复检查、晚期返工和无效收尾显著缩短墙钟时间。
2. 已有规则未执行时，优先判定为 `execution_failure`，先修执行链，不重复堆规则。
3. 日常工作能自行适应的问题，不必自动固化进 Cabinet；只有无法稳定自愈、重复出现或明确属于规则缺口的问题，才进入正式版本候选。
4. LAB 允许连续迭代 `v1.5.5-lab.N`；失败实验直接撤回，不层层叠补丁。必要时进入 `v1.5.5-rc.N`，最终由用户明确定稿为 v1.5.5。
5. 不同 T 级采用不同效率策略：轻任务重点减少无价值工作，高风险任务重点提高一次执行成功率；不得为了统一“变快”而削弱必要安全与质量 Gate。

## 2. 真实样本与问题池

### 2.1 样本 A：T2 单表任务

样本类型：T2，单一来源文件 → 单一 Excel 成品。  
结果：质量 PASS；实际墙钟约 13 分钟。  
判定：质量无问题，效率不可接受；属于流程型性能问题，不以降低质量换速度。

### 2.2 样本 B：T7 Runtime 单向部署

样本类型：T7，GitHub Stable → Mac Runtime 的机械单向部署与验收。  
结果：最终部署 PASS；边界、回滚、Agent 同步、状态凭证和最终安装检查均通过。  
过程表现：正确的高风险 Gate 基本保留，但发生了数次可避免的机械折返，包括正式源环境发现较晚、维护边界脚本首次调用方式错误、PATH 解析异常、sidecar 校验工作目录错误等。  
判定：质量与安全边界无问题，但执行确定性和机械鲁棒性仍需提高。T7 的优化目标不是删掉必要 Gate，而是“该做的一项不少，并尽量一次做对”。

### 2.4 两类样本的共同结论

- T1-T2 的主要优化方向是**少做无价值工作**：减少过度规划、重复验收、晚期返工和冗余收尾。
- T7 等高风险任务的主要优化方向是**提高一次执行成功率**：必要的源身份、回滚、同步、状态与最终安装 Gate 继续保留，但环境探测、脚本入口、工具定位、工作目录等机械步骤应尽量第一次就正确。
- 两类样本共同指向：当前 Cabinet 的主要瓶颈正在从“规则缺少”转向“既有规则能否被稳定、确定地执行”。因此 lab.1 优先修执行确定性，不以增加 Markdown 条款数量作为优化成果。

## 3. v1.5.5-lab.1 执行覆盖

### 3.1 T1-T2 本机任务路径

除非用户明确指定其他工作目录，本机文件型任务的任务根统一放在：

`/Users/macbook/ChatGPT/workspace/`

一项任务一个任务夹。原稿、过程件与正式成品继续按现有 Office Delivery 分区；不得直接把普通任务目录创建在 `/Users/macbook/ChatGPT/` 根下。

### 3.2 首次写入前完成一次性预检

T1-T2 文件任务在第一次生成成品前一次性锁定：

- 用户要求的目标格式；
- 最终目标目录；
- 最终正式文件名；
- 是否存在宿主真实强制 Hook／交付登记；
- 本轮唯一必要验收项。

命名规则能在生成前判断的，必须在生成前判断；禁止“成品已经制作和验收后才发现文件名不合规”这一类晚期返工。

### 3.3 快车道必须真正走快车道

满足 T1-T2 确定性文件条件时：

- 内部完成定级后直接执行，不单独发送完整计划阶段消息；
- 不为形式创建 Task Card、Review Gate、Delivery Contract 或检查旁文件；
- 宿主真实强制要求的登记只执行必要的一次，并与 Cabinet 自身可选流程分层；
- 不因底层 PDF／Excel 等工具有自己的说明，就叠加第二套完整规划与复核流程。

### 3.4 验收一次化与硬停止

默认执行链：

`原稿保护 → 一次生成 → 一轮联合验收 → 必要宿主登记 → 交付并停止`

联合验收一次完成当前任务真正需要的：内容／口径、公式或结构、可打开性、视觉必要检查、最终名称与路径、最终目录状态。

规则：

- 平台已经给出可复用的技术校验结果，不重复跑同类检查；
- 联合验收 PASS 后，没有实体变化就不得再次重开、重渲染、重扫公式、重算哈希或重新做同类目录审查；
- 如果确有返工，只复验改动项及其直接受影响项，不整轮重跑；
- 宿主 Gate PASS 后，如其结果已覆盖对应事实，不再为了“最终确认”重复同类检查；
- 正式成品目录禁止生成检查旁文件；确需检查产物放 `work/`／scratch，并优先避免生成无价值旁文件。

### 3.5 完工小结收敛

T1-T2 默认只向用户报告：

- 完成了什么；
- 正式成品文件名与真实位置；
- 关键验收结论；
- 真实存在的未完成项／限制（没有则简洁写无或直接省略）。

默认不展开内部契约、门禁、SHA、脚本、宿主状态、重复检查过程等机械细节，除非这些信息影响交付、用户明确要求，或属于实质失误处置。

“未完成项”与“可选后续”不得混写。未经用户要求，不主动在完工小结追加“按单位拆分、增加汇总、继续补数据”等新任务菜单。

总耗时只有在存在可靠计时且对当前实验／用户决策有价值时报告；没有可靠计时不为了格式机械输出“无法精确核实总耗时”。

### 3.6 T7 部署机械链确定性

T7 等高风险机械部署不使用 T1-T2 的“少做”逻辑削弱安全 Gate，而采用“必要步骤一次做对”的实验策略。

部署写入前尽量在一轮只读预检中同时确认：

- 正式源实际位置与 Git 工作树状态；
- 目标 commit / branch 身份及远端可达性；
- 当前 Runtime 的版本、commit、摘要与 `SYNCED / STALE / DRIFTED` 状态；
- 回滚工具、维护边界入口、解释器与关键机械命令的实际可用位置；
- 本次必须保留的部署、Agent 同步和最终安装 Gate。

执行规则：

- 已知维护脚本必须从其正式支持入口首次正确调用，不先试未经规则支持的执行方式；
- 环境存在 PATH 不确定性时，关键部署/回滚/哈希命令优先使用已验证的明确路径或由正式脚本内部解析，不在失败后才临时修正；
- sidecar、manifest、状态文件等校验应绑定明确绝对路径或声明的工作目录，避免因当前 CWD 偶然变化产生假失败；
- `STALE` 可以按既有部署合同继续，`DRIFTED` 仍必须停止；不得为了减少步骤跳过源身份、回滚快照、Agent `--check`、状态凭证和最终 installation check；
- 单个机械步骤失败后只修正该步骤和直接依赖，不重新跑已经有可信证据且未受影响的前置 Gate。

## 4. 自我进化新逻辑

### 4.1 日常自适应优先

生产任务中的自我进化首先表现为“执行得更好”，而不是“每次都生成一份自我进化报告”。

允许在既有边界和规则内：

- 当前任务发现重复步骤后立即收敛后续步骤；
- 后续同类任务直接采用已经验证的更短执行路径；
- 发现既有规则已经覆盖问题时，按既有规则执行，不新增重复规则。

这类自适应不等于修改 Stable，不产生正式 EVO，也不自动写正式 Cabinet。

### 4.2 问题状态

LAB 使用三种主要观察状态：

- `OBSERVE`：真实出现过，但可能属于偶发执行偏差、运行时因素，或模型已经能够自行适应；继续用真实任务观察。
- `CONFIRMED`：重复出现、影响明显、已有规则仍无法稳定执行，或证据明确表明存在规则缺口／冲突；可以进入实验候选。
- `RESOLVED-BY-ADAPTATION`：后续可比真实任务中稳定不再复发，且无需修改 Stable；从正式版本候选中退出，但保留实验记录供回溯。

高影响首次问题可以直接 CONFIRMED；普通问题原则上不因一次任务就自动写正式规则。

### 4.3 从问题到正式版本

流程改为：

`真实问题 → OBSERVE / CONFIRMED → 日常适应验证 → LAB 实验（必要时） → 保留 / 继续观察 / 撤回 → RC（可选） → 用户明确 FINAL → 正式 v1.5.5`

只有不能靠日常自适应稳定解决的问题，才值得进入正式 Cabinet 变更。

已有规则未执行时：

`execution_failure → 先修执行链 / 路由 / 加载 / 停止条件 → 再验证`

不得直接复制一条内容相同的新规则来“加强语气”。

### 4.4 自我进化报告

不设置“每个生产任务固定输出自我进化报告”的要求。

用户可见的进化信息遵循：

- 普通适应：不额外报告；
- LAB 观察：只在当前实验讨论或用户要求时报告；
- 正式 EVO：继续沿用现有 Evolution Policy，只在真实正式晋升成功后显示 EVO 行。

因此，原问题 1.5.5-002 不再定义为“交付报告缺一个章节”，而定义为“需要正确区分日常适应、LAB 实验与正式 EVO”。

## 5. LAB 版本治理

- 正式 `main` 在本轮保持 v1.5.4，不因实验自动漂移。
- 实验版本使用 `v1.5.5-lab.N`；必要时使用 `v1.5.5-rc.N`；正式版本仍使用三段 SemVer `v1.5.5`。
- 每个 lab 版本必须明确：实验假设、相对生产版的最小差异、真实任务证据、质量结果、墙钟结果（可可靠取得时）、异常、结论。
- 结论仅允许：`KEEP`、`OBSERVE`、`REVERT`。
- `lab.N+1` 不自动等于所有历史 lab 的累加；只继承已经有证据支持的最小有效组合。
- 失败实验可直接丢弃实验分支；不得为了保住实验而向 Stable 叠补丁。
- 模型／推理档切换属于独立实验变量；未经用户明确选择，不由 Cabinet 自动换型或降档。速度收益必须用同类真实任务实测，不用设计预期冒充结果。

### 5.1 证据优先级

LAB 的主要证据来自真实工作，不以自造 Demo 的高通过率代替生产验证。

- **真实工作样本是主证据**：用于判断实际质量、墙钟时间、返工次数、流程折返、运行时兼容和问题是否真正复发。
- **Demo / 合成回归是辅助证据**：用于证明已知规则和修复在受控条件下未明显破坏，可以帮助定位和防回归，但不能单独证明某项优化已经成功。
- `KEEP`、`RESOLVED-BY-ADAPTATION` 以及进入 RC 的关键结论，原则上必须有可比真实任务支持；只有 Demo PASS 时，最多说明“理论路径可行／未发现受控回归”，不能标记生产问题已解决。
- 不为凑样本专门制造大量工作；继续以正常办公和真实部署自然积累证据。

## 6. lab.1 验收指标

质量门槛：不得低于 v1.5.4；正式成品仍须真实可用、口径正确、路径正确、目录干净、原稿受保护。高风险部署的源身份、回滚、同步与最终安装 Gate 不因性能优化而降低。

效率指标：以约 13 分钟 T2 样本作为轻任务首个基线；T7 部署暂不以“步骤越少”衡量，而以必要 Gate 完整、机械折返减少、一次执行成功率提高为主。后续同类任务有可靠墙钟时再比较。

重点观察：

1. T1-T2 是否从一开始就进入 `/Users/macbook/ChatGPT/workspace/`；
2. T1-T2 是否在首次写入前确定最终文件名；
3. T1-T2 是否只执行一轮联合验收；
4. 是否在 PASS 后立即停止；
5. 完工小结是否只保留用户真正需要的信息；
6. 已有规则未执行的问题能否通过执行适应稳定消失；
7. 若问题不再复发，是否能够标记 `RESOLVED-BY-ADAPTATION` 而不继续给 Cabinet 加规则；
8. T7 部署能否在写入前一次性识别正式源、Runtime 状态和关键工具入口；
9. `maintenance_boundary.py` 等正式维护入口能否首次正确调用；
10. PATH、CWD、sidecar 等机械环境问题是否在后续真实部署中不再造成折返；
11. 在提高 T7 执行确定性的同时，源身份、回滚、Agent 检查、状态凭证和最终安装检查是否完整保留；
12. Demo PASS 是否始终只作为辅助证据，而不是替代真实工作的完成判定。

## 7. 当前结论

v1.5.5-lab.1 的目标不是“增加更多规则”，而是验证：

> 同样的任务、同样的质量边界，通过更严格执行已有快车道、前置路径与命名、一次验收、硬停止、提高高风险机械链的一次执行成功率，以及日常适应优先、真实工作优先的进化机制，让实际工作更快、更稳、更少依赖用户纠正。
