# Review System

Review 核对用户要求与真实结果，不核对执行者是否“看起来努力”。主代理总审同时检查少做与多做。

## 独立性与强度

- T1-T3 按风险自检；其中 T1-T2 快车道只做一轮联合自检／抽检，不为“独立性”另起第二套技术检查。用户显式要求独立审阅时按要求执行。
- 正式完整稿件，或向正式材料新增制度、审批、职责与协作规范，至少按 T4 审核；不能仅凭执行者填写 T3 豁免。范围明确、无新增依据或风险的局部微改，以及无正文改写的确定性单文件转换除外。
- T4-T6 至少一名未承担最终写入的独立审核者；T7+ 至少两条不同维度的独立判断路径。
- T9-T10 在阶段内先审候选，再验实际落地；复验只覆盖变化与未决项，不重读未变化全库。完成后停止，不自动进入下一阶段。

## 取证顺序

1. **需求与边界**：对照用户原话、材料、目标文件、授权动作与排除项；既有源文件须核 `00_原稿/`、归档数量及清单。
   同时检验业务理解：是否抓住材料实际用途和领导需要判断的事项，是否把往年评价写成未来计划、把空白误判为未完成、遗漏用户已确认的口径，或混淆总部与下属职责；既查机械停笔和过度追问，也查无依据地认定完成、补造业绩。只修正影响当前交付的误判，不另建流程。
2. **真实候选**：读取当前成果，核内容、路径与哈希；需要查事实时使用来源定位，关键疑点定向回源。先独立判断，再看执行者解释或其他评审意见。
3. **内容**：事实、数据、日期、主体、引用、逻辑、结构、语气、前后一致性、样本映射与附件关系。未读到不猜；“多做”的无关章节或动作也列为问题。
   交付前通读实际成稿及拟发送回复，横向比较相邻、同类段落和表格行，检查重复起句、同构句式、机械收尾及不增加信息的总结套话；发现后删去冗余或按具体事项重写，再核事实和覆盖是否保留。必要的统一术语、固定字段及指定格式不作机械去重；检查纳入现有自检或独立审核，不另增审核轮次。
4. **文件与原件**：验证实际文件、源与副本一致性、原件未覆盖、格式与可打开性。平台原生能力已经完成并留下可复用结果的结构检查、OCR／提取、渲染或技术校验，不为独立性再次调用同类工具；审核者只对用户验收项、关键风险点及发现的异常做独立判断。只有证据缺失、结果冲突、工具失败或高风险任务需要时才定向重跑受影响检查，不得用禁用工具补门禁。
5. **成品与目录**：T1-T2 快车道且宿主未强制持久化契约时，直接以用户当前要求作为 Expected，核唯一 Actual 的格式、名称、路径、可打开性和最终目录；不为同一结论补建 Task Card／Delivery Contract。非轻量任务或强制契约任务才读取 Task Card `deliverables` 作为 Expected、Delivery Contract `artifacts` 作为 Actual，并按 `artifact_id` 对账。最终目录只留正式成品和用户明确要求的附件，原稿、过程件、审核 JSON、日志、测试件、缓存、锁和临时转换件不得混入。
6. **完工回复**：核拟发送给用户的完工小结，至少有真实完成内容、成品及路径、目录／归档状态、关键核验、未完成或限制、实际耗时或无法核实原因。有实质失误时必须说明处置；无实质失误不制造反思。
7. **裁决**：给 PASS／FAIL／BLOCKED、发现、证据及未核项。主代理裁决冲突，修复后只定向复验。

## 真实证据门禁

仅在任务等级、用户要求或宿主强制门禁确实需要独立审核时使用 [Review Gate](../templates/review-gate.json)。使用时，候选清单须绑定实际文件及 SHA-256；每个审核者须有真实运行标识、判断维度和可读取的结果证据。交付门禁的 `reviews` 每项须提供 `evidence_path`、`evidence_sha256` 和非空 `source_ref`（工具／消息定位）；证据必须为 JSON，内含与声明一致的 `reviewer_id`、`author_id`、`verdict`、`must_fix`、`candidate_sha256`、`source_ref`。脚本读取真实证据字节核哈希，再比对结论与当前成果；定位仅为溯源声明，不冒充身份认证。运行 ID、时间戳、固定等待、字数或预登记 PASS 单独均不能证明完成。

`must_fix` 必须是数组；类型错误不得当空数组。当前候选发生实质变化时使对应审核失效并复验。不能只比对双方自填的同一个 hash，必须读实际候选重新计算。没有可读取的审核证据时，明确未核验，不伪造独立性。

正式契约任务中，`source_archive_gate.required=true` 且状态不是 PASS、源或副本未核、待修项非空、问题解决但尚未复验时，均不得 PASS。原稿不得是转换稿、接受修订稿或元数据清理稿。快车道仍必须实际通过原稿归档门禁，但不为证明已通过再生成一套 Review Gate 文件。

## Task Root Archive 与 FINAL PASS

正式归档的审阅对象包含两层：任务根目录和任务内部目录。任务根必须是 `YYYY-MM-DD_任务主题/`，日期等于最近一次实质性工作日期；`new-chat`、`temp`、`tmp`、`untitled`、`working`、`未命名`、`临时` 及根目录未知项均使 Archive=FAIL。跨日续办和 Delivered 后 Reopen 必须沿用同一 `task_instance_id`、同一根目录和历史正式版本，只原地更新日期、材料批次及下一版本。

审核按 [Office Delivery](../domain-skills/office-delivery.md) 的十一项最终化条件和脚本接口逐项取证：确认当前 Actual、历史保留报告、材料批次和最终路径一致，内容／技术验收证据真实可读，未知输入已解决。正式 `check()` 或 Hook 失败即 Finalization=FAIL；`check_components()` 只证明局部组件，不证明最终归档。独立审核不得仅抄写执行者的 PASS。

## 返工与交付

失败项与其依赖单独返工。非轻量任务一般最多三轮修复复验，仍无进展报告 PARTIAL／BLOCKED；短任务不机械进入三轮循环。T1-T2 快车道发现局部问题时只修受影响处并复验受影响分页／对象；发现系统性转换问题时切换一次合适的替代路径或报告限制，不连续叠加多套工具逐页试错。审阅授权不等于测试可修改共享目录或访问 API。

文件型任务如出现以下任一情况，必须在交付前返工，不能用说明文字豁免：

- 用户要求实体成品但实际没有最终文件；
- 快车道成品与用户当前要求的格式、名称或位置不一致；
- 正式契约任务中 Task Card 锁定的必交成品少交、错版本、错格式、错角色、错目录或错指定文件名；
- 正式契约任务的 Actual 出现 Task Card 未授权的正式成品；
- 用户已改变交付要求但仍沿用失效的旧 Expected／契约；
- 最终目录混入未授权过程文件、日志、证据、缓存或测试产物；
- 应保留的原稿、必要成品或用户指定附件没有进入约定位置；
- 没有完工小结，或小结没有真实路径和核验状态。

非轻量任务交付前核对开工小结是否实际给出 T 级、目标、预期交付、目标位置和停止条件；快车道不要求为了形式补发独立开工小结。正式契约 `incident_present=true` 时，除处置文字还须以 `incident_records` 指向现有 INC 记录的绝对路径；门禁读取并核对编号、record 权限、失败类型及非空证据，复用现有事故记录，不另建台账。无实质失误不强制记录文件。实际耗时优先核消息时间戳；缺可靠时间则声明无法精确核实。只有已建立或宿主强制的文件交付契约才按 `scripts/delivery_gate.py` 检查；不为了证明快车道成功临时新建契约再跑一次 Gate。PASS 不证明声明真实、业务正确或脚本被宿主强制调用。

正式正文与交付说明分开。完成说明列真实结果、路径、自检和限制；阶段任务另列尚未处理项目、建议的最小下一阶段与恢复所需文件，然后停止。

正式契约任务的文件留存门禁复用契约中的 `retention.process_root`（任务专用过程目录，无过程文件才用 null）、`temporary_files` 与 `retained_reason`。脚本检查该目录内实际文件及输出根的直接子项，漏报项不通过；必要证据也须注明留存理由。CLI 自动排除本次契约文件，宿主直接调用时传 `contract_path`；不扫描其他任务，不跟随目录软链。快车道只保留原稿、最终成品和实际必要的过程项，不为留存检查制造额外过程文件。
